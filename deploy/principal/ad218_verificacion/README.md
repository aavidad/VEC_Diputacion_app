# Comprobación previa de AD218

AD218 tiene historia. La migración `000218_carga_convoca_bolsa.up.sql` conserva su SHA256 `0cbf0ca49be98cae576e5b0e7cce8d279955f4ce9aa898420016f2b7a0379608`. No se modifica, reaplica ni revierte para mejorar el aviso de instalación.

Antes de considerar una instalación, el DBA ejecuta `deploy/postgresql/autorizacion_atestada_v3/pruebas_sql/ad218_estado_previo.sql` en la base de destino con PostgreSQL 18, por el canal local autorizado. El verificador sólo lee catálogos. Si muestra **«AD218 pendiente»**, la preimagen POST216 coincide y la entrega puede seguir sus controles habituales. **«AD218 ya instalada»** detiene una segunda UP. Un estado mixto también detiene la entrega e indica la clave y las huellas observadas para investigarlo. El resultado de este verificador no autoriza por sí solo a instalar SQL.

Al restaurar una copia, `pg_dump` y `pg_restore` de una base existente no reponen automáticamente las ACL de la **base** creadas fuera de su contenido. El DBA conserva el inventario privado de roles, concesiones y tipos de fila, repone las ACL de la nueva base y compara `aclexplode(pg_database.datacl)` en ambos sentidos con la fuente. La diferencia debe ser cero, incluidos otorgante, privilegio y opción de concesión. También coteja propietarios, ACL y tipos de fila exigidos por el procedimiento de restauración. No aplica permisos por nombre de cargo ni concede `PUBLIC` para hacer pasar un ensayo.

La guarda B1 del núcleo comprueba `CONNECT` del LOGIN técnico en la base actual. Si la ACL de base no se repone, responde `42501` aunque las funciones y las tablas estén restauradas. En una copia aislada, retirar `CONNECT` al grupo Bolsa dentro de una transacción produjo ese rechazo y ROLLBACK dejó la ACL idéntica. `ad218_nucleo_directo.sql` usa material sintético y `SET SESSION AUTHORIZATION` dentro de ROLLBACK: comprueba el rechazo y la ausencia de efecto, pero no equivale a una conexión autenticada nueva ni prueba TLS, firma, B79 o una asignación de rol publicada.
