# Catálogos configurables: primera migración

Este esquema conserva versiones publicadas de categorías y sus usos. Aporta la autoridad común que necesita RPT; no importa el fichero de demostración ni declara aprobadas sus categorías. La publicación administrativa, sus dos aprobaciones y las fachadas nominales de escritura siguen pendientes. AD3-117 solo añade lecturas.

## Instalación y ensayo

`roles_up.sql` precede a `migraciones/000001_autoridad_categorias.up.sql`. Para etapa0, la lista causal completa está en `deploy/principal/lista_sql_trabajo_codexd_rpt_escritura_v3_20260930.txt`: roles → 000001 corregida → 000002 → AD3-117 → 000003 → AD3-126. Los archivos 000002 y AD3-117 publicados en `main` forman parte de la base de código; su presencia en Git no demuestra que estén instalados. El paquete H6 los excluye junto al resto de RPT, por lo que el clon nuevo los recibe una sola vez en esta secuencia. La migración exige el rol `vec_autorizacion_atestada_v3_propietario` y el esquema vacío creado por `roles_up.sql`. No consulta tablas de Contratación, Bolsa ni Personal. Dirección ensaya la lista en el clon de la principal antes de integrar. `pruebas_sql/000001_autoridad_categorias.sql` está destinada a una base desechable: usa datos sintéticos y revierte la transacción. El `DOWN` rechaza cualquier publicación, control, uso o historia y deja el esquema vacío para repetir el `UP` en una base desechable. `roles_down.sql` retira el esquema vacío y los roles. Ninguno de los dos se ejecuta sobre una instalación con datos.

`roles_up.sql` acepta los privilegios de `PUBLIC` que ya tenga la base o el esquema `public`. No los cambia: crea `vec_catalogos_configurables` y revoca `PUBLIC` solo en ese esquema. `pruebas_sql/roles_up_acl_public.sql` comprueba esta frontera en una base desechable con los roles aún ausentes y retira los roles al terminar.

## Contrato interno de escritura

Las cuatro funciones de escritura son internas y fijan `search_path=pg_catalog, pg_temp`. La migración comprueba al terminar su propietario, configuración y ACL exacta. Solo el propietario `NOLOGIN` de AD3 V3 recibe `EXECUTE`; ninguna cuenta de aplicación recibe acceso a tablas o funciones. Las futuras fachadas nominales deben consumir una decisión V3 vigente antes de invocar el núcleo en la misma transacción. De ese motivo atestado obtienen el último argumento `motivo_ref` con la forma `catalogo_id:version:entrada_clave`, validada como `ReferenciaEntradaCatalogo.Referencia()`; la decisión conserva la huella del catálogo. El núcleo rechaza referencias mal formadas y no deduce el motivo del material del cliente.

Cada fila de `historia` guarda el motivo original y los estados anterior y posterior. En una publicación nueva o una reserva, el anterior es nulo; la confirmación o cancelación pasa de `reservado` al estado terminal. Deshabilitar pasa de `habilitada` a `deshabilitada`, cobertura conserva `deshabilitada` y tombstone pasa a `tombstone`. Un replay autorizado puede usar un motivo de acceso nuevo, pero devuelve el recibo previo sin modificar la historia del efecto original. La auditoría V3 del nuevo acceso es distinta de esa historia local.

| Función interna | Entrada y efecto |
| --- | --- |
| `publicar(text, integer, text, text, jsonb, text, text, text, text, text, text, text) → text` | ID, versión consecutiva, SHA-256 y JSON canónico; preimágenes y su huella; dos aprobaciones, actor, decisión, recibo y motivo atestado. Exige preimagen exacta de cada categoría existente. Una nueva no admite preimagen. Publicar otra versión no rehabilita una categoría deshabilitada. |
| `reservar(text, text, text, text, integer, text, text, text, text, text) → text` | Consumidor, identidad estable de uso, categoría, publicación exacta, actor, decisión, recibo y motivo. Reserva antes del efecto. `(consumidor, uso_ref)` no se reutiliza; su replay devuelve el recibo original, incluso tras deshabilitar la categoría. |
| `terminar_uso(text, text, text, text, text, text, text, text) → text` | Consumidor, identidad de uso, recibo de reserva, estado `confirmado` o `cancelado`, actor, decisión, recibo terminal y motivo. Hace CAS `reservado → terminal`; un confirmado no puede cancelarse. El consumidor debe acreditar su efecto antes de confirmar, o su ausencia definitiva antes de cancelar: la firma interna no demuestra esa evidencia por sí sola. |
| `cambiar_proyeccion(text, bigint, text, text, bigint, text, text, text, text) → bigint` | Categoría, revisión esperada, acción, cobertura, total histórico, actor, decisión, recibo y motivo. Deshabilitar cierra reservas nuevas. Cobertura rechaza reservas pendientes o un total inferior a los usos confirmados; su atestación por conciliación propietaria sigue pendiente. Tombstone exige cobertura, `total_historico_declarado = 0` y ningún uso reservado ni confirmado. No borra publicaciones, usos cancelados ni historia. |

El adaptador de cada consumidor conserva su referencia opaca, ID, versión, huella y recibos. Debe reservar antes del efecto; tras una respuesta ambigua, recupera la misma identidad y comprueba el resultado antes de confirmar o cancelar. La conciliación de cobertura necesita hechos de cada módulo por un puerto autorizado. La ausencia de filas en este esquema no demuestra ausencia de usos antiguos.

## Límite de este corte

El acta H1 previa confirmó la ausencia de estas migraciones antes de instalar las seis rutas RPT en el clon. Este parche no acredita instalación en la principal. La 000001 no concede acceso HTTP ni instala publicación, provisión o escritura nominal. La huella de la publicación identifica los bytes canónicos recibidos; la aprobación y la firma legal requieren sus circuitos propios. La RPT no está editable ni operativa por integrar esta fuente.

## Lecturas internas 000002 y AD3-117

La migración 000002 añade tres funciones internas: lista de categorías habilitadas para un uso nuevo, publicación histórica por referencia exacta y estado de una reserva por `(consumidor, uso_ref, reserva_recibo_ref)`. Solo el propietario de AD3 V3 recibe `EXECUTE`. La lista pagina por `categoria_id`, devuelve la versión y huella de cada fila y conserva una publicación canónica de anclaje incluso si la página está vacía. Las demás publicaciones se deduplican frente al anclaje. El límite de 100 filas y 48 MiB, incluido el recibo AD3, protege la respuesta; el núcleo reserva 4 KiB para esa envoltura y la fachada comprueba el tamaño final. Es un presupuesto técnico, no una regla de negocio. La lectura histórica conserva el documento original y muestra el control actual por separado.

AD3-117 añade las tres fachadas nominales sobre AD3-114. Cada llamada exige decisión V3 actual, perfil activo, audiencia, finalidad, acción, recurso y material exactos; consume y audita antes de leer en la misma transacción. El módulo del descriptor configurado se coteja con cada publicación canónica devuelta. La consulta de uso exige además el consumidor propio del rol técnico de CT, Bolsa o Personal. Las fachadas no publican concesiones ni aceptan el perfil desde HTTP. Sin descriptor ID/módulo gobernado y concesión positiva aprobada para la persona y su perfil vigente, la operación permanece denegada. El adaptador Go y los consumidores aún deben conectarse; este SQL no convierte la RPT en editable.

El llamador fija `TimeZone=UTC`, `statement_timeout=15s` e `idle_in_transaction_session_timeout=20s` mediante `SET LOCAL` antes de la invocación V3. Las fachadas no cambian el temporizador de sentencia dentro de la llamada: el núcleo comprueba esos límites, y un ajuste posterior al inicio de la sentencia no sustituye el límite real del LOGIN.
