# Catálogos configurables: primera migración

Este esquema conserva versiones publicadas de categorías y sus usos. Aporta la autoridad común que necesita RPT; no importa el fichero de demostración ni declara aprobadas sus categorías. La publicación administrativa y sus dos aprobaciones siguen pendientes del caso de uso y del wrapper AD3-117.

## Instalación y ensayo

`roles_up.sql` precede a `migraciones/000001_autoridad_categorias.up.sql`. La lista causal está en `deploy/principal/lista_sql_trabajo_codexd_rpt_gobierno_sql_20260929.txt`. La migración exige el rol `vec_autorizacion_atestada_v3_propietario` y el esquema vacío creado por `roles_up.sql`. No consulta tablas de Contratación, Bolsa ni Personal. Dirección ensaya la lista en el clon de la principal antes de integrar. `pruebas_sql/000001_autoridad_categorias.sql` está destinada a una base desechable: usa datos sintéticos y revierte la transacción. El `DOWN` rechaza cualquier publicación, control, uso o historia y deja el esquema vacío para repetir el `UP` en una base desechable. `roles_down.sql` retira el esquema vacío y los roles. Ninguno de los dos se ejecuta sobre una instalación con datos.

`roles_up.sql` acepta los privilegios de `PUBLIC` que ya tenga la base o el esquema `public`. No los cambia: crea `vec_catalogos_configurables` y revoca `PUBLIC` solo en ese esquema. `pruebas_sql/roles_up_acl_public.sql` comprueba esta frontera en una base desechable con los roles aún ausentes y retira los roles al terminar.

## Contrato del consumidor AD3-117

Las cuatro funciones del esquema son internas. Solo el propietario `NOLOGIN` de AD3 V3 recibe `EXECUTE`; ninguna cuenta de aplicación recibe acceso a tablas o funciones. AD3-117 debe exponer wrappers nominales con `SECURITY DEFINER`, `search_path` fijo y concesiones por rol técnico exacto. Cada wrapper consume y revalida una decisión V3 para acción, recurso, ámbito, finalidad, actor y sesión dentro de la misma transacción que invoca la función y escribe la auditoría central. El recibo local de `historia` acompaña esa auditoría; no la sustituye. Un replay también requiere autorización actual: el wrapper pasa la nueva decisión al core, devuelve el recibo original y audita el nuevo acceso sin reescribir la historia del primer efecto. La aplicación abre una transacción de escritura con límites de bloqueo y sentencia; confirma únicamente tras recibir el recibo de la operación completa.

| Función interna | Entrada y efecto |
| --- | --- |
| `publicar(text, integer, text, text, jsonb, text, text, text, text, text, text) → text` | ID, versión consecutiva, SHA-256 y JSON canónico de dominio; mapa administrativo de preimágenes y su SHA-256; dos referencias de aprobación, actor, decisión y recibo. Cada categoría existente exige en el mapa `version`, `huella_sha256`, `revision` y `estado` exactos. Una categoría nueva no admite preimagen. El mapa queda fuera del documento canónico y se conserva junto a la publicación; su huella se calcula sobre `preimagenes::text` en PostgreSQL. Un cambio de control rechaza toda la publicación. El estado `deshabilitada` sigue cerrado a nuevas reservas tras publicar otra versión; rehabilitar requiere una operación nominal futura. AD3 debe comprobar que ambas aprobaciones son de personas distintas y vinculan la huella del documento con la huella del mapa de preimágenes. |
| `reservar(text, text, text, text, integer, text, text, text, text) → text` | Consumidor, identidad estable de uso, categoría, ID/versión/huella exactos, actor, decisión y recibo. Reserva antes del efecto del consumidor. La identidad `(consumidor, uso_ref)` no se reutiliza. Un replay idéntico devuelve el recibo original, incluso tras deshabilitar la categoría. |
| `terminar_uso(text, text, text, text, text, text, text) → text` | Consumidor, identidad de uso, recibo de reserva, estado terminal `confirmado` o `cancelado`, actor, decisión y recibo terminal. Hace CAS `reservado → terminal`; un replay idéntico devuelve el recibo. Confirmar exige evidencia del efecto propio del consumidor; cancelar exige acreditar que no ocurrió. |
| `cambiar_proyeccion(text, bigint, text, text, bigint, text, text, text) → bigint` | Categoría, revisión esperada, acción `deshabilitar`, `cobertura` o `tombstone`, referencia de cobertura, total histórico, actor, decisión y recibo. Devuelve la revisión nueva. Deshabilitar cierra nuevas reservas. Cobertura exige que el reconciliador haya comprobado todos los consumidores históricos; incluso el total cero requiere evidencia. Rechaza cobertura con reservas pendientes o por debajo de los usos confirmados registrados. Tombstone exige cobertura y cero reservas pendientes. La publicación y los usos permanecen. |

El adaptador de cada consumidor usa su propia referencia opaca y conserva ID, versión, huella, clave y recibos. Debe registrar una reserva durable antes de producir un efecto externo; tras respuesta ambigua, recupera la misma identidad y comprueba el efecto antes de confirmar o cancelar. El reconciliador de cobertura obtiene hechos de cada módulo por su puerto autorizado y entrega a AD3 una atestación verificable. No se presupone que la ausencia de filas en este esquema pruebe ausencia de usos antiguos.

## Límite de este corte

La migración 000001 no concede acceso HTTP ni instala el caso de uso de publicación. La huella de la publicación identifica los bytes canónicos recibidos; la aprobación y la firma legal requieren sus circuitos propios.

## Lecturas internas 000002 y AD3-117

La migración 000002 añade tres funciones internas: lista de categorías habilitadas para un uso nuevo, publicación histórica por referencia exacta y estado de una reserva por `(consumidor, uso_ref, reserva_recibo_ref)`. Solo el propietario de AD3 V3 recibe `EXECUTE`. La lista pagina por `categoria_id`, devuelve la versión y huella de cada fila y conserva una publicación canónica de anclaje incluso si la página está vacía. Las demás publicaciones se deduplican frente al anclaje. El límite de 100 filas y 48 MiB, incluido el recibo AD3, protege la respuesta; el núcleo reserva 4 KiB para esa envoltura y la fachada comprueba el tamaño final. Es un presupuesto técnico, no una regla de negocio. La lectura histórica conserva el documento original y muestra el control actual por separado.

AD3-117 añade las tres fachadas nominales sobre AD3-114. Cada llamada exige decisión V3 actual, perfil activo, audiencia, finalidad, acción, recurso y material exactos; consume y audita antes de leer en la misma transacción. El módulo del descriptor configurado se coteja con cada publicación canónica devuelta. La consulta de uso exige además el consumidor propio del rol técnico de CT, Bolsa o Personal. Las fachadas no publican concesiones ni aceptan el perfil desde HTTP. Sin descriptor ID/módulo gobernado y concesión positiva aprobada para la persona y su perfil vigente, la operación permanece denegada. El adaptador Go y los consumidores aún deben conectarse; este SQL no convierte la RPT en editable.
