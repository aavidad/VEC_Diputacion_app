# Captura lógica local de PostgreSQL — CS04

`vec-copias-capturar` ejecuta `pg_dump` por cada base configurada y
`pg_dumpall --globals-only`. Conserva propietarios, roles, membresías, ACL,
constraints, triggers y funciones. Crea archivos privados y un documento
`captura-parcial.json`. Nunca presenta ese documento como copia completa,
válida, cifrada o restaurable.

Esta CLI sirve para ensayos locales con datos sintéticos. No tiene permisos
ADMIN, registro durable de operaciones ni auditoría administrativa. La marca
`ensayo_local_sintetico` confirma el alcance elegido por el operador; no concede
autorización. Una composición operativa deberá conectar las autoridades CS07/08.

## Preparar el ensayo

Compile el binario con el toolchain instalado, sin descargar dependencias:

```bash
GOPROXY=off GOSUMDB=off go build -p 8 -o /ensayo/vec-copias-capturar ./cmd/vec-copias-capturar
/ensayo/vec-copias-capturar -config /ensayo/config.json
```

Prepare un PostgreSQL 18 aislado, sin acceso a redes externas ni montajes de bases
conservadas. El descriptor y el inventario siguen el formato de
`cmd/vec-copias-inventariar/README.md`. Los archivos instalados se miden de nuevo
mediante CS02 dentro de la ventana. Las migraciones y el alcance PostgreSQL
siguen siendo declaraciones de ese inventario; esta CLI observa realmente la
versión del servidor y de las herramientas, pero no atesta todo el inventario SQL.

Las herramientas `pg_dump`, `pg_dumpall` y `psql` deben figurar en el inventario
con sus SHA256 y versiones exactas. También se mantienen las herramientas que
exige CS01 (`pg_restore` y `postgres`). No se acepta solo una versión mayor.

Cree un directorio privado de bloqueos, compartido por todas las capturas del
mismo origen en el mismo host. La referencia de origen debe coincidir con
`postgresql.cluster_ref`. El directorio de captura debe ser nuevo: no se borra
ni sobrescribe una captura anterior.

configuración del operador y no pueden proceder de una petición web o un

Actualice la ventana antes de ejecutar. `PGHOST` admite únicamente socket local
o loopback. No se hereda el entorno del proceso; se rechazan `PGPASSWORD`,
servicios de conexión indirectos y variables de inyección. Si necesita contraseña,
use `PGPASSFILE` externo con los permisos que exige PostgreSQL. No escriba secretos
en argumentos, catálogos, informes o Git.

`testdata/escritor/main.go` ofrece un escritor de ensayo: inserta filas reales
en `prueba.eventos` y usa un cierre de admisión protegido por `flock`. `close`
espera la operación en curso, `drain` y `check` comprueban el cierre bajo el mismo
bloqueo, y `open` permite continuar. Solo sirve para esta fixture. Los servicios
VEC requieren controles propios para todas sus instancias, migradores,
despachos, tareas y edición de configuración; no basta devolver cero desde un
comando ni activar una casilla de mantenimiento.

Para reproducir esa fixture, prepare en la base sintética `fixture`:

```sql
CREATE ROLE fixture_owner NOLOGIN;
CREATE ROLE fixture_reader NOLOGIN;
CREATE SCHEMA prueba AUTHORIZATION fixture_owner;
CREATE TABLE prueba.eventos (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  dato text NOT NULL DEFAULT chr(65),
  CONSTRAINT dato_check CHECK (length(dato) > 0)
);
ALTER TABLE prueba.eventos OWNER TO fixture_owner;
GRANT USAGE ON SCHEMA prueba TO fixture_reader;
GRANT SELECT ON prueba.eventos TO fixture_reader;
GRANT USAGE ON SEQUENCE prueba.eventos_id_seq TO fixture_reader;
GRANT CONNECT ON DATABASE fixture TO fixture_reader;
```

Cree `/ensayo/writer` privado, compile el helper con
`go build -p 8 -o /ensayo/escritor ./cmd/vec-copias-capturar/testdata/escritor/main.go`
y arranque `/ensayo/escritor writer /ensayo/writer`. El helper espera PostgreSQL
18 en `/var/run/postgresql`, base `fixture` y usuario sintético `postgres`.
El directorio y las herramientas del ejemplo se ajustan en la configuración
privada. Detenga ese proceso al terminar el ensayo.

## Secuencia y archivos

La aplicación adquiere la exclusión, cierra admisión, drena y comprueba escritores.
Observa CS02 y aplica CS01 antes del volcado. Mantiene la exclusión mientras
ejecuta los comandos y vuelve a comprobar escritores e inventario al terminar.
Ante cancelación intenta reabrir con un contexto de limpieza independiente y
limitado; un fallo de reapertura no devuelve captura terminada.

Los archivos son `base-0.dump` (y siguientes), `globals.sql` y
`captura-parcial.json`, con permisos `0600` dentro del directorio `0700`.
Globals puede contener material secreto de los roles. El documento parcial
incluye huellas y tamaños privados; stdout solo comunica una clave de catálogo,
la cantidad de componentes y tres valores siempre falsos: `completa`, `valida`
y `publicable`. Los textos de las claves están en
`web/static/textos/{es,en}/copias_captura.json`.

El código de salida es cero si termina la captura parcial y uno si falla. Los
errores contienen claves estables, sin stderr PostgreSQL ni rutas. Un fallo
puede dejar archivos parciales privados; no crea el documento de terminación.
Consérvelos para diagnóstico y retire solo los recursos propios del ensayo.

## Continuar con captura física

`application/capturacopias.Servicio` acepta un puerto opcional
`CapturadorComponentes`. Ejecuta su `Capturar(ctx, inventario)` después de la
captura lógica, dentro de la misma exclusión y ventana. CS05 debe exigir y
acreditar parada limpia de PostgreSQL antes de copiarlo, y reactivarlo antes de
retornar para permitir el inventario y las comprobaciones finales. No se libera
la ventana entre lógico y físico. Incluso con componentes adicionales, el
resultado permanece parcial hasta cifrado, autenticación y las dos
restauraciones verificadas de CS03/06.

Para la copia previa de una sustitución, el propietario servidor usa
`AbrirVentana(ctx, peticion)`, `CapturarEnVentana(ctx, ventana)` y después
`ComprobarVentana(ctx, ventana, peticion)` antes del siguiente efecto. Conserva
esa capability opaca hasta terminar y llama a `CerrarVentana(ventana)` incluso
si falla o vence el contexto. La operación, el origen y la huella de la preimagen
deben ser los mismos; una ventana cerrada, fabricada o usada para capturar otra
vez se rechaza. No hay reapertura automática durante la sustitución. El control
operativo de reapertura debe comprobar que PostgreSQL está disponible antes de
reanudar escritores; la CLI lógica de este corte no detiene PostgreSQL.

## Evidencia local del 1 de octubre de 2026

Ensayo en dos contenedores propios `postgres:18.4-bookworm`, imagen
`sha256:0a314d409a9633cff4f89dc18482262625c0ee78cb1aa2ff8e47bc6da0251e1b`,
sin red externa, rootfs de solo lectura, PGDATA en tmpfs y límites de 1 CPU,
512 MiB y 128 procesos. No se usaron bases ni configuraciones conservadas.

La CLI capturó 18.389 filas mientras el escritor real estaba excluido. Otro
cluster vacío recibió globals y el dump mediante:

```bash
psql -U fixture_bootstrap -d postgres -v ON_ERROR_STOP=1 -f /ensayo/captura/globals.sql
pg_restore -U fixture_bootstrap --exit-on-error --create --dbname=postgres /ensayo/captura/base-0.dump
```

Se recuperaron las 18.389 filas, IDs 1–18.389 sin huecos, contenido esperado en
todas las filas y secuencia `18389/is_called=true`. Se comprobaron propietarios,
roles y ACL de base, esquema, tabla y secuencia. Una inserción que incumplía la
CHECK fue rechazada. Los fallos de check, tamaño máximo y exclusión simultánea
devolvieron error y no dejaron un documento de terminación; los dos primeros
reabrieron el escritor.

Esta evidencia comprueba la captura lógica de la fixture. No acredita CS06,
recuperación física, arranque de VEC, cifrado, autenticidad, idempotencia durable,
exclusión entre hosts, compatibilidad productiva ni el inventario de Sistemas.
